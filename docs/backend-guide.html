01

자바 개발자용 TypeScript 속성 정리

TS는 “타입이 붙은 JavaScript”야. 클래스·인터페이스·제네릭·데코레이터 같은 건 자바와 거의 대응되고, 대신 타입은 컴파일 때만 존재하고 런타임엔 사라진다는 게 가장 큰 차이야 (그래서 Nest가 데코레이터로 런타임 메타데이터를 따로 심어).

02

NestJS 핵심 개념 6가지

Nest는 구조가 스프링과 매우 닮았어 — DI 컨테이너, 계층 분리, 데코레이터 기반. 아래 6개만 잡으면 이 코드 전부 읽혀.

개념하는 일스프링 대응이 프로젝트 예시

실제 컨트롤러 한 조각이 어떻게 읽히나

// memo-items.controller.ts — 이 프로젝트 실제 코드
@Controller('memo-items')   // → 경로 /api/memo-items
@UseGuards(JwtAuthGuard)  // 이 컨트롤러 전체에 JWT 인증 필수
export class MemoItemsController {
  constructor(
    @InjectRepository(MemoItem)          // DI로 리포지토리 주입
    private readonly items: Repository<MemoItem>,
  ) {}

  @Patch(':id')                        // PATCH /api/memo-items/3
  async update(@Param('id') id, @Body() dto: UpdateMemoItemDto) {
    // dto는 Pipe가 이미 검증함. 여기선 로직만.
  }
}

경로 앞에 /api가 붙는 건 main.ts의 app.setGlobalPrefix('api') 때문이야. 포트는 5004.

04

이 프로젝트의 분류 방식

코드는 기능(도메인)별 모듈로 나뉘어 있어. 폴더 하나 = 한 관심사, 그 안에 entity · controller · service · dto가 같이 있어. “한 도메인을 이해하려면 그 폴더만 보면 된다”가 핵심.

backend/src/
├─ main.ts            // 부팅: 포트 5004, /api, CORS, ValidationPipe
├─ app.module.ts      // 루트 모듈 (DB 연결 + 하위 모듈 조립)
├─ auth/              // 인증 도메인
│   ├─ auth.service.ts       // 로그인·회원가입·비번 (bcrypt)
│   ├─ auth.controller.ts
│   ├─ auth.dto.ts
│   └─ jwt-auth.guard.ts     // 토큰 검사
├─ users/
│   └─ user.entity.ts
└─ tasks/             // 스케줄 도메인 전체 (가장 큼)
    ├─ task.entity.ts + tasks.controller.ts + tasks.service.ts
    ├─ memo-item.entity.ts   + memo-items.controller.ts
    ├─ mind-topic / month-memo / week-item / period-item / recurring
    └─ hidden-folder.entity.ts
“도메인으로 나누면 MSA가 쉽나?” — 솔직한 답 맞아, 하지만 이건 MSA가 아니라 “모듈러 모놀리식”이야. 도메인별로 경계를 잘 그어두면 나중에 한 모듈을 떼서 별도 서비스로 만들기가 쉬워지는 건 사실이야. 그치만 지금 규모에선 모놀리식이 정답이고, 섣부른 MSA는 오히려 독이야(네트워크·트랜잭션·배포 복잡도 폭증). 지금처럼 도메인 경계만 깔끔히 유지 → 필요해지면 그때 분리, 이게 실무 정석이야.

참고: 지금 tasks 모듈이 여러 컨트롤러를 다 안고 있어서 조금 비대해. 규모가 더 커지면 memo, planning 같은 서브모듈로 쪼개는 게 다음 리팩터링 후보야.

05

DB ERD

테이블 9개. 모든 테이블이 users에 매달려 있고(실제 FK, onDelete: CASCADE), tasks는 여러 “소스” 테이블을 논리적으로 참조해(그냥 int 컬럼 — DB FK는 아님). 아래에서 실선은 진짜 FK, 점선 설명은 코드상 논리 참조야.

실선(||--o{) = 실제 FK · 점선(||..o{) = 코드상 논리 참조(FK 아님)

테이블을 3덩어리로 이해하기

  • 실행 단위 — tasks: 특정 날짜의 할일. 완료·타임박싱·Top3·Schedule이 다 여기.
  • 생성 소스 — recurring_items(반복) · week_items(주간) · period_items(기간): 규칙에 따라 tasks를 자동 생성. 생성된 task는 recurringId 등으로 원본을 가리켜.
  • 메모/기획 — memo_items(월×분류 항목, 상·하위 self 참조) · month_memos(월 메모) · mind_topics(집중 주제) · hidden_folders(숨긴 폴더).
전 테이블 공통 패턴 모든 테이블에 createdAt·deletedAt이 있어. 삭제는 물리 삭제가 아니라 soft delete(@DeleteDateColumn → deletedAt에 시각 기록, TypeORM이 조회 시 자동 제외). 데이터는 안 지워지고 감춰질 뿐이야.
06

어디서부터 읽으면 되나

  • 1. main.ts → app.module.ts: 앱이 어떻게 조립되는지 (10분)
  • 2. auth/ 폴더 통째로: 가장 작고 완결된 도메인 — Nest 한 바퀴가 다 들어있어 (entity→dto→service→controller→guard)
  • 3. tasks/task.entity.ts + tasks.controller.ts: 제일 중심 테이블
  • 4. memo-items.controller.ts: 상·하위 self 참조 + 완료 전파 로직이 있어 실전 감각 잡기 좋아

읽다가 데코레이터가 헷갈리면 “이건 스프링의 뭐랑 같지?”로 치환하면 대부분 풀려. 구조가 정말 닮았거든.
